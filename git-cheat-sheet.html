01 — Définition

Qu'est-ce que Git ?

Git est un système de contrôle de version distribué. Chaque développeur possède une copie complète du dépôt, historique inclus. On peut travailler hors ligne et synchroniser ensuite.

Git stocke des instantanés (snapshots) complets à chaque commit, pas des diffs. Chaque commit reçoit un SHA-1 unique calculé à partir de son contenu.

  • DistribuéPas de serveur central obligatoire — chaque clone est complet
  • SnapshotsChaque commit = état complet de l'arbre de fichiers
  • SHA-1Identifiant de 40 caractères hex, infalsifiable
  • BranchesSimples pointeurs sur un commit — création quasi instantanée
  • HEADPointeur indiquant la position courante dans l'historique
  • IndexAutre nom du Staging Area — la zone de préparation des commits

02 — Setup

Configuration initiale & SSH

À faire une seule fois sur chaque nouvelle machine. Ces réglages sont globaux (--global) et s'appliquent à tous vos dépôts. La clé SSH remplace l'authentification par mot de passe pour chaque push.

git config — identité, éditeur, comportements
  • git config --global user.name "Prénom Nom"Identité affichée sur chaque commit — doit correspondre à votre compte plateforme
  • git config --global user.email "mail@example.com"Email associé aux commits
  • git config --global core.editor "code --wait"VS Code comme éditeur pour les messages longs
  • git config --global init.defaultBranch mainBranche initiale nommée main (et non master)
  • git config --global pull.rebase truegit pull = fetch + rebase — évite les commits de merge parasites
  • git config --global push.autoSetupRemote truegit push sans --set-upstream sur la première fois — Git ≥ 2.37
  • git config --listAfficher toute la configuration active (globale + locale)
  • git config --global --editOuvrir ~/.gitconfig dans l'éditeur
Clé SSH — connexion sans mot de passe

SSH authentifie votre machine auprès de GitHub / GitLab / Azure DevOps. Une fois configuré, plus aucun mot de passe à chaque push.

  1. 1.
    Générer la clé (ED25519 — algorithme recommandé)
    ssh-keygen -t ed25519 -C "mail@example.com"
  2. 2.
    Copier la clé publique
    cat ~/.ssh/id_ed25519.pub
  3. 3.
    Coller sur la plateforme
    GitHub → Settings → SSH and GPG keys
    GitLab → Preferences → SSH Keys
    Azure DevOps → User Settings → SSH public keys
  4. 4.
    Tester la connexion
    ssh -T git@github.com
Ajouter la clé publique (.pub) sur la plateforme — jamais la clé privée.
Aliases — raccourcis personnalisés

Les aliases transforment une commande longue en un raccourci court. Définis dans ~/.gitconfig, ils sont disponibles dans tous les dépôts.

  • git config --global alias.lg "log --oneline --graph --all --decorate"Historique graphique compact — la plus utile au quotidien
  • git config --global alias.st "status"git st au lieu de git status
  • git config --global alias.co "checkout"git co feat/x au lieu de git checkout feat/x
  • git config --global alias.br "branch"Lister et naviguer entre les branches rapidement
Template ~/.gitconfig complet
[user] name = Prénom Nom email = mail@example.com [core] editor = code --wait [init] defaultBranch = main [pull] rebase = true [push] autoSetupRemote = true [alias] lg = log --oneline --graph --all --decorate st = status co = checkout br = branch

Résolution de conflits

Un conflit survient quand deux branches ont modifié la même zone d'un fichier et que Git ne peut pas choisir automatiquement quelle version garder. Git insère alors des marqueurs dans le fichier et attend que vous tranchiez.

Anatomie d'un conflit
<<<<<<< HEAD result = compute_mean(values) ======= result = compute_weighted_mean(values, w) >>>>>>> feat/weighted-metrics
<<<<<<< HEAD — début de votre version (branche courante)
======= — séparateur entre les deux versions
>>>>>>> — version entrante (branche mergée / rebasée)
Procédure de résolution
  1. 1.Ouvrir le fichier — VS Code affiche "Accept Current · Accept Incoming · Accept Both" directement dans l'éditeur
  2. 2.Choisir la bonne version ou combiner les deux manuellement — supprimer absolument tous les marqueurs (<<<, ===, >>>)
  3. 3.git add <fichier> — indiquer à Git que ce fichier est résolu
  4. 4.git merge --continue ou git rebase --continue — reprendre l'opération
Commandes clés
  • git statusLister les fichiers en conflit — marqués both modified
  • git diffAfficher tous les marqueurs de conflit restants dans les fichiers
  • git merge --abortAnnuler l'opération de merge — revenir à l'état exact d'avant
  • git rebase --abortAnnuler le rebase en cours — revenir à l'état d'avant
  • git checkout --ours <fichier>Accepter entièrement votre version (HEAD) pour ce fichier
  • git checkout --theirs <fichier>Accepter entièrement la version entrante pour ce fichier
04 — Conventional Commits

Préfixes de commit

La convention Conventional Commits impose un format structuré aux messages de commit : <type>(<scope>): <description>. Un bon commit répond à « qu'est-ce que ce code fait ? » — au présent impératif, en minuscules, sans point final, sous 72 caractères. Le type indique la nature du changement et permet de générer des changelogs automatiquement.

Préfixe Usage Exemple
featNouvelle fonctionnalité métier (endpoint, algorithme, page)feat(auth): ajouter l'authentification OAuth2
fixCorrection de bug — comportement incorrect ou erreurfix(pipeline): corriger le calcul sur les nulls
docsDocumentation uniquement, sans toucher au code fonctionneldocs(readme): mettre à jour l'installation
styleFormatage, espaces, virgules — sans changement logiquestyle: ruff format sur src/
refactorRestructuration sans ajout de feature ni correction de bugrefactor(loader): extraire la normalisation
testAjout ou correction de tests, sans toucher au code de prodtest(loader): ajouter les tests unitaires
choreMaintenance : dépendances, config CI, outils de devchore(deps): mettre à jour pandas 2.2.0
perfOptimisation des performances sans changement fonctionnelperf(query): optimiser le batch processing
ciModification d'un fichier de pipeline CI/CDci: ajouter le lint step à la pipeline
revertRetour arrière sur un commit précédentrevert: annuler la migration défectueuse

Format : <type>(<scope>): <description impérative, ≤72 car., minuscule, sans point final>

05 — Stratégie

Branches

Une branche Git est un simple pointeur sur un commit — la créer ne copie aucun fichier, c'est quasi-instantané. Le principe de base : une tâche = une branche, la plus courte possible. Plus une branche vit longtemps, plus elle diverge de main et plus les conflits s'accumulent. On ne travaille jamais directement sur main ou dev.

mainProduction — code stable et déployéPermanente
devIntégration — reçoit toutes les PR de featurePermanente
feature/Nouvelle fonctionnalité3–5 jours max
fix/Correction de bug3–5 jours max
refactor/Restructuration sans changement visible3–5 jours max
hotfix/Bug critique en production — créée depuis mainQuelques heures
docs/Documentation uniquement1–2 jours
chore/Dépendances, CI, config — sans impact métier1–2 jours
experiment/Exploration — pas forcément destinée à mergerLibre
Hiérarchie & flux de travail
feature/x ──┐ fix/y ├──► dev ──► main → prod refactor/z ──┘
Flux complet
  1. 1.Créer depuis dev : git checkout -b feature/x
  2. 2.Travailler, commiter, pousser
  3. 3.PR feature/x → dev — code review
  4. 4.Merge dans dev après approbation
  5. 5.PR dev → main — validation finale
  6. 6.Merge main → déploiement automatique CI/CD
Hotfix (bug critique prod)

Detached HEAD — qu'est-ce que c'est ?

HEAD est le pointeur de position dans l'historique Git. En temps normal il pointe sur une branche, qui elle-même pointe sur un commit — tout nouveau commit avance la branche automatiquement. En état « detached HEAD », HEAD pointe directement sur un commit, sans branche intermédiaire. Git affiche un avertissement et vous permet d'inspecter ou tester cet état, mais tout commit créé ici sera orphelin : il n'appartient à aucune branche et disparaîtra au prochain git checkout si vous ne créez pas de branche pour l'ancrer.

État normal
HEAD ──► main ──► commit abc123 HEAD pointe sur la branche, qui pointe sur un commit Tout commit créé avance la branche automatiquement
Detached HEAD
HEAD ──► commit abc123 (pas de branche !) HEAD pointe directement sur un commit Tout nouveau commit sera "orphelin" et perdu au prochain checkout
Quand ça arrive
  • git checkout <sha>Naviguer vers un commit précis
  • git checkout v1.0.0Naviguer vers un tag
  • git checkout HEAD~3Remonter dans l'historique
Sortir du detached HEAD
  • git checkout mainRetourner sur une branche normale
  • git checkout -b <nom>Créer une branche depuis cet état — garde les commits créés
En entretien : un detached HEAD n'est pas une erreur — c'est utile pour inspecter l'historique. Le danger est d'y commiter sans créer de branche : ces commits disparaissent au prochain checkout.

07 — Concepts clés

Comparaisons à maîtriser

Ces quatre paires de concepts sont parmi les questions d'entretien les plus fréquentes sur Git. Il ne suffit pas de connaître la définition : il faut savoir quand utiliser l'un plutôt que l'autre et être capable de l'expliquer avec un schéma ou un exemple concret.

Merge vs Rebase

git merge
A──B──C──────M main \ / D──E──' feat M = merge commit (commit de fusion)
  • +Non-destructif — l'historique exact est préservé
  • +Idéal pour intégrer une branche via PR/MR
  • –Crée un commit de merge qui charge l'historique
  • –Historique non-linéaire, difficile à lire sur de gros projets
Quand l'utiliser : pour intégrer feat → dev → main via PR/MR
git rebase
A──B──C──────D'──E' feat \ D──E ← commits originaux rejoués D' et E' ont de nouveaux SHA
  • +Historique linéaire et propre — plus lisible
  • +Pas de commit de merge parasite
  • –Réécrit l'historique — SHA des commits changent
  • ⚠Jamais sur une branche partagée avec d'autres devs
Quand l'utiliser : pour mettre à jour sa branche locale : git fetch origin && git rebase origin/main

08 — Annuler & corriger

Modifier un commit · Reset · Reflog

Git offre plusieurs niveaux d'annulation selon que le commit est local ou déjà partagé. Règle d'or : --amend, rebase -i et reset réécrivent l'historique — réservés au travail avant le push. Pour annuler quelque chose de déjà poussé, la seule option sûre est git revert, qui crée un nouveau commit d'annulation sans toucher à l'existant.

Modifier un commit
ObjectifCommande
Corriger le message du dernier commitgit commit --amend -m "nouveau msg"
Ajouter un fichier oublié (sans changer le msg)git add <f> && git commit --amend --no-edit
Fusionner des commits WIP avant pushgit rebase -i HEAD~N → fixup
Réécrire un message plus anciengit rebase -i HEAD~N → reword
Réordonner des commitsgit rebase -i HEAD~N → changer l'ordre des lignes
Supprimer un commitgit rebase -i HEAD~N → drop
⚠ Règle absolue : --amend et rebase -i réécrivent l'historique — ne jamais les utiliser sur des commits déjà pushés sur une branche partagée.
git reset — les 3 modes
ModeWorking DirStagingCommits
--soft intact intact annulés
--mixed (défaut) intact vidé annulés
--hard effacé ⚠ effacé ⚠ annulés
  • --soft HEAD~1Défaire un commit, modifs restent stagées — pour le resplitter ou corriger
  • --mixed HEAD~1Défaire commit et staging, modifs restent dans le working dir
  • --hard HEADAnnuler toutes les modifs non-commitées — irréversible sans reflog
reset vs revert : reset réécrit l'historique (local uniquement). git revert <sha> crée un nouveau commit d'annulation — la seule option sûre après un push.
git reflog — le filet de sécurité

Le reflog enregistre tous les mouvements de HEAD localement — y compris après un reset --hard ou une branche supprimée par erreur. Conservé 90 jours. N'est pas pushé vers le remote.

git reflog abc1234 HEAD@{0}: reset: moving to HEAD~1 def5678 HEAD@{1}: commit: feat(auth): token ghi9012 HEAD@{2}: commit: fix: null check
Récupérer un état perdu
Après un reset --hard par erreur :
git reflog → trouver le SHA → git reset --hard <sha>
Branche supprimée par erreur :
git reflog → SHA du dernier commit → git checkout -b ma-branche <sha>
Cherry-pick d'un commit perdu :
git reflog → SHA → git cherry-pick <sha>
09 — Travail en équipe

Bonnes pratiques

Les réflexes qui évitent les accidents en équipe. Les scénarios varient selon la taille de l'équipe et l'organisation des branches, mais les principes restent constants : ne jamais travailler directement sur les branches partagées, synchroniser souvent, et protéger main et dev avec des politiques côté serveur.

2 devs · même branche

Stash → Pull → Stash Pop

  • 1Mettre de côté ses modifs : git stash
  • 2Récupérer les modifs du collègue : git pull origin <branche>
  • 3Réappliquer ses modifs : git stash pop
  • !Conflit après pop → résoudre → git add → git stash drop
10+ devs · grande équipe

Fetch → Rebase (pas pull)

  • 1Télécharger sans toucher au local : git fetch origin
  • 2Rejouer ses commits dessus : git rebase origin/main
  • 3Pousser après rebase : git push --force-with-lease
  • !git pull = fetch + merge → commits de merge inutiles dans l'historique
Protections de branches

Règles à activer sur main & dev

  • Interdire les push directs — tout passe par PR/MR
  • Exiger au moins 1 reviewer par PR
  • Exiger que la CI soit verte avant le merge
  • Interdire le force push sur main
  • Réinitialiser les approbations si nouveaux commits
Règles d'or

À respecter en toutes circonstances

  • Jamais de commit direct sur main ou dev
  • Rebase pour mettre à jour sa branche locale, merge via PR pour intégrer
  • Jamais de rebase sur une branche partagée avec d'autres
  • --force-with-lease au lieu de --force — vérifie qu'on n'écrase pas le travail d'un collègue
  • Branches courtes : 3–5 jours max, sinon découper en sous-tâches
  • git revert (pas reset) pour annuler un commit déjà pushé
